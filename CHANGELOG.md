## 8.0.0

Release preparation only. API date: `2026-09-07`. Candidate contract: Flint `f811ffc6cb584c5b280a5c9f561075e77a1bc664`, exported from a clean checkout with SHA-256 `c605f5699b2e109badac53deff456d091e6c7499a2f294b7f339006e43bcc614`. Generator: `7713b37e9bcdf63dbb6242e33c5c5ca4bbd8d323`, unchanged from beta.3. Production contract SHA: `<PRODUCTION_SHA_AT_RELEASE>`. Stable publication waits for the remaining area breaks, production deployment, and consumer approval. Re-pin to the deployed SHA and revalidate before release.

Changes since `8.0.0-beta.3` (Flint `323766dba32c7945254bbcc0ff23b160f4076b18`):

- `paymentIntents.confirm` accepts the checkout session's `checkoutToken`. A normal checkout credential can start or continue only its own session's legs; a recovery credential can only continue its holding attempt without `payment_source`. Checkout credentials cannot send `save_payment_method`, even as false, or `buyer_ip_address`. Follow `managed_by_owner` and its next action for payments collected through their owner.
- New confirmations default to `client_action_type: "url"`; omitted continuation options retain the existing type. Handle both `client_action.type` members, `url` and `stripe`, and read expiry from the containing pending action. Reader payments still require Stripe actions. Zero-balance order setup can continue with `action: "setup"` and no `setup_payment_source`.
- Invoice payment intents add `invoice_schedule_entry_id`. Invoice collection conflicts identify the payment intent, and `paymentIntents.cancel` cancels an eligible invoice payment. Order resume, `is_resumable`, invoice payment-attempt methods, `CollectInvoiceResult.invoice_payment_attempt`, and invoice-attempt events remain available. The parked retirements are excluded.
- Order `version` is a persisted concurrency counter, starting at 1 for new orders. Use the latest returned value as `expected_version` or `expected_order_version`; never derive it from `updated_at`. Several changes can share a wall-clock update time. Expanded resources and external observations can change independently of a resource's owned-state version.
- Subscription and plan `quantity` multipliers and `quantity_options` are removed, including checkout terms and payment-link previews. Set quantities on identified lines. Quantity changes require 1 to 50 distinct `line_items`; signup and plan changes identify plan lines, while changes to existing subscriptions identify subscription lines. Subscription line PATCH no longer edits quantity. This includes FLI-737 `a1b67aa2ff`, the snapshot used by CLI 0.20.0.
- One-time secrets and URLs may be omitted on a replay by another credential. Guard access to optional API-key, customer-session, partner-app, access-link, upload, and merchant-account-session secret fields. Idempotency replay and recovery behavior also changed; review the [migration notes](MIGRATION.md#changes-in-the-800-candidate-since-beta3).

Other generated changes include the buyer email-change list's buyer-specific response model, required `MerchantBillingBalance.past_due_money` and `ReadinessRequirements.upcoming_due`, and optional billing and readiness deadlines. Node's `CreateMeSubscriptionPreviewRequestQuantityChange` alias is replaced by `CreateSubscriptionPreviewRequestQuantityChange`. Remove subscription multiplier getters from PHP response, request, and webhook models as well as direct calls. The complete comparison against reconstructed published beta.3 reports **287 breaking, 652 review, and 33 additive findings** (972 total). Review these as one 8.0 major; the report does not certify production compatibility.

The `payment_source` union (saved Flint method, Stripe ConfirmationToken, Stripe PaymentMethod, or reader), the `url`/`stripe` action union, and flattened `paymentIntents.create({ order_id, ... })` are retained from beta.3. All 721 source operations remain, with 720 selected; the sole exclusion is the browser-only OAuth consent redirect. See the [8.0 migration guide](MIGRATION.md#sdk-800) for the full upgrade from 7.x. No tag or package is published by this preparation.

## 8.0.0-beta.3

Version `8.0.0-beta.3` updates both SDKs to Flint `main` at `323766dba32c7945254bbcc0ff23b160f4076b18`, with API date `2026-09-07` and generator `7713b37e9bcdf63dbb6242e33c5c5ca4bbd8d323`. This is a prerelease on npm `next`; `latest` stays on `7.0.0`. Install `@flintpay/node@8.0.0-beta.3` or `flintpay/flint:8.0.0-beta.3`. The packages select 720 of 721 source operations; only the browser-only OAuth consent redirect is excluded. Use a backend serving this pinned contract. Review the [8.0 migration guide](MIGRATION.md#sdk-800), including the [changes since beta.2](MIGRATION.md#changes-in-800-beta3).

Payment actions now expose the closed `client_action` union with `type: "url"` or `type: "stripe"`. Check `type` and the member fields before reading `stripe`; open URL actions as a redirect, popup or iframe. Read `expires_at` on the containing pending action. Order payment attempts and order pay responses carry `pending_actions`; standalone payment-intent confirmation carries `current_payment_action`. The `client_action_type` request option selects `url` or `stripe`; reader credentials support only `stripe`. This SDK accepts either action so a backend can change its default without a decoding failure.

Migration changes since beta.2:

- With merchant credentials and `payments.payment_intents.write`, `paymentIntents.confirm` now confirms a single order leg through the existing payment-intent route, including checkout and replacement-order legs. Its request and response match standalone confirmation. Omit `payment_source` to continue the holding attempt; use order `pay` for multiple unpaid legs or selected gift cards. Checkout credentials still use order `pay` and `resume`. Read `supported_actions` for stored owner facts; it can change without advancing the intent version. Replace refusal reason `order_owned` with `managed_by_owner` and follow `remediation.next_actions`: invoice owners name `collect_invoice`, and subscription owners name `create_subscription_payment_retry`. Saving a card on an order leg requires an order customer and `payments.payment_methods.write`.

- Replace checkout-specific delivery calls with delivery quote and selection resources. Invoice and return-resolution checkout creation now use checkout-session creation and return the session directly. Buyer credit-note PDF calls take only the credit-note path ID. Use `orders.listCharges`, `orders.listLineItems` and `webhookEndpoints.signDelivery` for the current method names.
- Replace `orders.createPaymentIntent(orderId, params)` with `paymentIntents.create({ order_id: orderId, ...params })`. Its result is the payment intent itself, with `payment_collection` beside its fields. Confirmation accepts `payment_source` instead of top-level credential fields; omit it to continue the attached source. Order payment-intent selections use the same nested credential. The old `token` credential is removed; use `stripe_payment_method` with `stripe.payment_method` for an app-collected Stripe PaymentMethod, or another declared credential type.
- Move `orders.createFulfillment`, `fulfillments.createShipment`, `shipments.createPackage` and `fulfillments.createEvent` to `fulfillments.create`, `shipments.create`, `packages.create` and `fulfillmentEvents.create`, with the parent ID in the body. Create return children with `returnInspections.create`, `returnReceipts.create`, `returnDispositions.create` and `returnResolutions.create`, passing `return_id` in the body. The former `returns.create*` methods are removed. Restocking percentages must be 1 through 100.
- Read invoice monetary totals from `settlement_amounts`; `credit_money` becomes `credited_money` there and on invoice activities and schedule entries. Subscription plan and quantity previews rename `credit_money` to `credit_adjustment_money`. For `invoices.list` and `me.listInvoices`, replace sort value `outstanding_money` with `settlement_amounts.outstanding_money`.
- Webhook snapshots and previous attributes use payload-specific models and omit GET-only fields, including payment intent fee, net and collection guidance, checkout branding and URL fields, and invoice `public_url`. Fetch the resource for those fields. The invoice payment-attempt event is `invoice_payment_attempt.succeeded`, replacing `invoice_payment_attempt.settled`.
- Buyer payment intent and return models omit merchant `supported_actions`; merchant returns and subscriptions omit `buyer_actions`. Merchant payment intent summaries, invoice attempts, order attempts and subscription summaries expose `supported_actions`. Order payment attempts require `order_id`. Email preferences permit null `customer_id` and `version`; buyer fulfillments and packages omit `supported_actions`.
- Several response fields now exclude null, including wallet `client_setup`, payment-error `remediation`, gift-card purchase `configuration`, line fulfillment `profile`, subscription swap `unit_price_money`, subscription renewal `order_payment_attempt`, invoice collection `invoice_payment_attempt` and payment review `matched_risk_rule_id`. Payment review card brands omit `unknown`. Update response fixtures and null handling to the generated types.
- Partner app refresh tokens are replaced by 900-second merchant-bound tokens minted with `client_credentials`; use the partner OAuth helpers. Public organization routes, sandbox and onboarding API-key creation, and credit-note refund methods are removed. Refund credit notes with `refunds.create({ refund_type: "credit_note", ... })`. Lifecycle `transition` calls become named actions. Gift card loads and promotion codes have their own resources; buyer gift-card transaction reads take a required `gift_card_id` query param. `invoices.issue` and `fulfillments.create` now require a saved idempotency key. See the migration guide for replacements and credential setup.

Custom order and payment-link lines accept optional `product_type` (`physical`, `digital`, `service`, `fee`) on creation and update, without a default. Omission leaves a new line unclassified and preserves its classification on update; null and `gift_card` inputs are rejected. Responses expose nullable classification. Other additions include readers and card-present credentials, payment splits and platform fees, merchant signup and onboarding access links, customer email-change requests and buyer recovery reads, remembered-buyer lookup and revocation, invoice late-fee lists, subscription line-item lists and signup quantities. Customer access links accept delivery and lifetime options; inspect their delivery discriminator before reading a returned URL. ACH account types and modifier pricing scopes follow the current API vocabulary.

The generator supports operation callbacks, negative scalar query constraints and negated dictionary-key constraints, including callback request and strict response construction models. The complete compatibility comparison against reconstructed published `8.0.0-beta.2` reports 7,496 breaking, 24,031 review and 4,768 additive findings (36,295 total). The beta.1 and beta.2 entries below cover the earlier 8.0 calling convention, names, errors, integer types, result metadata, credentials and timeout changes from 7.0.0.

## 6.0.0

Version `6.0.0` makes retries and idempotency keys follow each operation's idempotency class and adds Flint webhook JWT verification. Reads and keyed writes make up to 3 attempts. Writes with an optional key get an SDK-generated `flint-sdk-` key reused across retries, the 33 writes that require a key need yours (TypeScript won't compile without `idempotencyKey`), and writes that take no key are sent once. Install with `npm install @flintpay/node` or `composer require flintpay/flint:^6.0`. In Node, `await verifyWebhookAsync(rawBody, headers, { endpointIds, baseUrl })` from `@flintpay/node` or `@flintpay/node/webhooks`, or `client.verifyWebhookAsync`, verifies ES256 JWT deliveries against your webhook endpoint IDs and keys from the API origin's `/.well-known/jwks.json`. In PHP, use `Webhooks::verifyDelivery` or `$client->verifyWebhookDelivery` with `endpoint_ids`. Under PHP-FPM, pass a PSR-16 `cache` or enable APCu so workers share keys. JWT verification applies once Flint sends JWT-signed deliveries, which production doesn't do yet; both verifiers keep accepting today's HMAC deliveries when you pass your `secrets`, and `verifyWebhook` and `Webhooks::verify` remain HMAC-only. ## 3.0.0

Version `3.0.0` is the first stable release of the 3.0 line, published under npm `latest` and as a stable Composer release. Install with `npm install @flintpay/node` or `composer require flintpay/flint:^3.0`. It is generated from the API contract pinned in [`spec/openapi.json`](spec/openapi.json); the API version remains `2026-09-07`. Upgrading from `2.0.0` also brings every change in the `3.0.0-beta` entries below. See [the migration guide](MIGRATION.md#sdk-300).

This release adds one error class per `kind`, under `errors` in Node (`errors.ConflictError`) and `Flint\Errors` in PHP. Each extends `SdkError`, and `kind` remains authoritative. In Node, `error.name` is now the subclass name. `verifyWebhook` (Node) and `Flint\Webhooks::verify` (PHP) verify deliveries without a client. Node exports `VerifiedWebhook`, `KnownWebhookEvent` and one `WebhookEvent<Name>` type per event. `payment_intent.*` webhooks now carry the full payment intent.

Breaking changes:

- Method params no longer accept credential headers such as `X-Checkout-Session-ID`, or `Flint-Version`. Pass credentials in client or request options. The SDK sets the version header itself.

- Many state-conflict codes now return 409 and raise `conflict` errors instead of `validation` errors.
- `INVALID_TOTALS` and `INVALID_LINE_ITEMS` are replaced by 500 `ORDER_TOTALS_UNAVAILABLE`.
- In invoice, order paid and merchant billing balance webhooks, money amounts are now int64 strings.
- Payment intent `risk` and `last_payment_error` are always present and can be `null`.
- Removed fields and changed units for delivery, tax, wallet and refund resources are listed in [the migration guide](MIGRATION.md#sdk-300).

## 3.0.0-beta.20261006230000

Version `3.0.0-beta.20261006230000` is generated from the API contract pinned at its release and changes the beta interface from `3.0.0-beta.20261006210100`, including breaking changes. Review these changes before upgrading:

- For hosted checkout, send buyers to `checkout_session.url`. Embedded sessions omit it and use `checkout_access.checkout_auth_token`, which hosted checkout doesn't need. `CheckoutAccess` no longer has `hosted_url`, and results from `checkoutSessions.create`, `paymentLinks.resolve`, `returnResolutions.getOrCreateCheckoutSession`, and `me.createReturnResolutionCheckoutSession` no longer include the deprecated `hosted_checkout`. Code that reads either fails TypeScript type checking. Results from `invoices.getOrCreateCheckoutSession` and `me.createInvoiceCheckoutSession` keep `hosted_checkout` as an optional field for hosted sessions only. It repeats `checkout_session.url` and `checkout_access.checkout_auth_token`, is deprecated, and will be removed.
- `expiration.expires_in_seconds` in `checkoutSessions.create`, `paymentLinks.create`, and `paymentLinks.update`, and `checkout.default_expires_in_seconds` in `settings.update`, accept 60 through 86,400 seconds. The Node and PHP SDKs reject other values before sending a request. The pinned OpenAPI contract lists `INVALID_EXPIRATION` for these operations and for `paymentLinks.resolve`.
- When a checkout session credential calls `orders.sendReceipt`, the pinned contract limits its recipients. If the order has an email on file, the credential can send only to that address, and a different `email` returns `ORDER_RECEIPT_EMAIL_ON_FILE`. Otherwise it can send to at most three distinct addresses over the order's lifetime, and a fourth address returns `ORDER_RECEIPT_RECIPIENT_LIMIT_REACHED`. Every receipt sent for the order through this method counts toward that limit, including failed deliveries and receipts sent with a secret API key. Merchant credentials can send to any address. `VERSION_CONFLICT` means the order's receipt history changed during the request; retry it.
- The pinned OpenAPI contract replaces `PAYMENT_REQUIRED` and `PAYMENT_CONFLICT` with `CHECKOUT_SESSION_SOURCE_REQUIRED` and `CHECKOUT_SESSION_SOURCE_CONFLICT` for checkout session requests that set none, or more than one, of `quick_pay_item`, `order_id`, and `subscription_plan_id`. Generated error code types drop the old codes but accept any string, so checks for them still compile and need updating. The types add `ORDER_CHECKOUT_SESSION_CHANGED`, which means the order's open checkout session changed while the request was running and the request can be retried, and `PAYMENT_ATTEMPT_REQUIRES_CAPTURE`, which means an authorized payment attempt must be captured or canceled before you retry. The contract also updates the error codes declared for checkout session, order, payment, and other operations. The SDKs don't list errors per method; [`spec/openapi.json`](spec/openapi.json) does.
- Generated `checkout_session.completed` event types now declare a required `order_id` and an optional `payment_intent_id` in `data`, alongside the existing `checkout_session_id`. Test events built from the `Webhook_checkout_session_completed_*Input` types or the `makeWebhook_checkout_session_completed_*` helpers must include `order_id`.
- `me.listFulfillmentEvents` requires `order_id`, matching the API, which already requires it. Pass the ID of an order that belongs to the customer session's customer. Calls that omit `order_id` now fail TypeScript type checking, and the Node and PHP SDKs reject them before sending a request. The pinned OpenAPI contract now lists the existing `PORTAL_ORDER_ID_REQUIRED`, `INVALID_ID`, `INVALID_PAGE_SIZE`, `INVALID_PAGE_TOKEN`, and `RESOURCE_NOT_FOUND` errors for this operation, and generated error code types include `PORTAL_ORDER_ID_REQUIRED`.
