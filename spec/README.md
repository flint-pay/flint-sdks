# Pinned SDK inputs

`openapi.json` is the complete, unmodified public versioned API export at Flint `0f83faf086dd659e279da39ae653918b38450ae5` on `main`, from the path and SHA-256 recorded in `../sdk.lock.json`. The API date is `2026-09-07`. All 615 operations and 246 incoming webhook declarations are retained. The packages select 610 operations; five form-only CLI/OAuth operations are outside the generator's supported request formats.

The profiles and synthetic HTTP/model cases incorporate `flint-pay/sdk-generator` revision `314de2ee5975e3a5cc7cf385babd23b84eb489fa`, `tests/providers/flint/`. That fixture uses an earlier API revision; the export here stays pinned independently. Package names, version `7.0.0`, namespace, positional request convention and `semver` release policy remain Flint's production settings. Thirteen operations with union request bodies require an explicit object-style override. `../scripts/profiles.mjs` derives the retry and idempotency settings from each operation's idempotency class in the export. Optional-key writes get an SDK-minted `flint-sdk-` key reused across retries, required-key writes need the caller's saved key, and operations without a key header send none. GETs and keyed writes make up to 3 attempts, retrying when no response arrived, when `error.remediation.retry` is `same_request`, or on 429, 500, 502, 503 and 504 without a Flint error body; other writes are sent once.

The five authentication profiles use complete alternatives from the pinned contract. Checkout uses bearer `checkoutToken`; the `apiKey` shortcut uses merchant bearer authentication. The contract no longer declares `ApiKeyHeader`, so there is no `merchantKey` profile. Profiles retain published method names across ID/route moves: the `developer` sandbox, auth context, request log, resource timeline and partner app methods keep their names on the canonical paths, and same-resource renames keep the previous names as deprecated aliases. `../tests/provenance.json` records source revisions, fixture origins, the reviewed operation migrations, the changes since 6.0.0, same-route renames and intentional form-flow exclusions. Inventory actions expose only the canonical transition methods. Eight moved cross-resource operations preserve their 3.0.0 primary bindings; the two Location aliases remain deprecated aliases of `locations.update`. The generator does not support cross-resource aliases or fixed body values.

The common profile's `overrides` are exact-equivalent provider corrections for constructs the pinned generator can't load, applied before reference resolution:

- Integer bounds of `2^63-1` on uint64/int64 inventory and error-detail fields are not safe integers. Each field is declared `int64` without the bound, which keeps the same `[minimum, 2^63-1]` range.
- Metadata `propertyNames` reject keys starting with `flint_` through `not`. They use the equivalent lookahead-free pattern instead.
- Partner app credential branches forbid the other credential fields with `false` schemas. They use `not` with `required` instead.
- `DeliveryEligibilityExpression` and `DeliveryZoneConfiguration` select one operator through recursive `$ref` alternatives that TypeScript can't type. Each alternative is replaced by its single required key; the closed parent keeps exactly one operator per node.

`../tests/full-http-cases.json` and `full-model-cases.json` are synthetic regression cases, not live transaction certification. `full-inventory.json` records the pinned export's inventory. Do not add private provider definitions or real request/response data.

To update the API, obtain the matching versioned public JSON export, record its exact upstream revision and SHA-256 in `sdk.lock.json`, and keep the version header consistent. Review authentication bindings, operation inventory, examples, overrides and fixture expectations together. To update the generator, pin its exact revision, run `npm run setup`, regenerate, and review the complete diff before release.
